大模型核心技术概念详解

大模型（LLM）核心技术概念系统梳理：Token、向量空间、自注意力机制、Context、RAG、Function Calling、MCP、Agent 与 Agent Skill。

大模型核心技术概念详解#

1.1 LLM（大语言模型）#

  • 全称：Large Language Model
  • 本质：庞大的数学函数，核心运行的是矩阵运算
  • 输入输出：接受数字输入，输出数字结果
  • 技术基础：基于 Transformer 内部架构训练（该架构源自 2017 年的论文《Attention Is All You Need》）
  • 工作原理：通过海量数据训练，学习文本中的统计规律，从而能够基于概率预测下一个 Token

1.2 Token（令牌）#

Token 是大模型处理文本的最基本单位

所有与大模型的交互都需要先经过 Token 化处理，它直接决定了 API 调用成本和文本长度限制

  • Tokenizer 的作用：在人类与大模型之间做"翻译"，负责编码与解码过程
  • 编码过程：
    1. 将文本切分成一个个 Token（基本语言单元）
    2. 针对 Token 进行映射得到数字，即Token ID
    3. 模型将 Token ID 转换为高维向量表示（这个过程才是向量化/Embedding）
    4. Token ID 组成一串列表送入模型进行运算
  • 解码过程：将模型输出的 Token ID 转换为人类可读的文字（不需要切分步骤）
  • 换算比例：1 个 Token≈0.75 个英文单词≈1.5~2 个汉字（不同 Tokenizer 略有差异）

1.3 向量空间与语义理解#

为什么大模型能明白我们的意图？

核心在于高维向量空间中语义的表示与计算

  • 向量表示：每个 Token 都会被映射到一个高维向量空间中的点
  • 维度与特征：向量的维度越高，能表示的事物特征越丰富，可以理解为它在向量空间中的位置越精确
  • 语义距离：语义相近的词在向量空间中的距离较近，语义无关的词距离较远
    • 例如："猫"和"狗"的向量距离较近（都是宠物），而"猫"和"汽车"的向量距离较远
  • 上下文感知：向量在经过数个 Transformer 层之后，每个 Token 的向量都会被更新，融入上下文信息
    • 例如：针对"在咖啡馆里，想要一杯星巴克"，"星巴克"这个 Token 的向量会因为周围有"咖啡馆"、"杯"、"想要"等词而被调整，更准确地表示"星巴克咖啡饮品"这个含义

1.4 自注意力机制#

Transformer 架构的核心

自注意力机制让模型能够关注输入文本中不同位置的信息，从而理解上下文关系

  • 三个核心组件：
    • Query：当前词的特征表示
    • Key：其他词的特征表示
    • Value：每个词的特征表示
  • 工作流程：
    1. 计算 Query 和 Key 之间的相似度，得到注意力权重
    2. 用注意力权重对 Value 进行加权求和
    3. 得到最终的上下文感知表示
  • 示例：
    • "星巴克"的特征：咖啡、品牌、价格高、聊天、电脑
    • 与其他词计算注意力权重后，会发现"杯"和"咖啡"与"星巴克"的关联度最高
    • 从而正确理解用户想要的是星巴克咖啡饮品，而不是咖啡馆或 Logo

二、核心能力与限制#

2.1 Context 与上下文窗口#

  • Context（上下文）：大模型每次处理任务时所接收到的信息总和
    • 包括：对话历史、用户问题、当前输出、工具列表、System Prompt 等
    • 可理解为大模型的临时记忆体
    • 大模型只能看到当前上下文窗口内的信息，窗口外的信息会被"遗忘"
  • Context Window（上下文窗口）：Context 能容纳的最大 Token 数量
    • 是大模型的核心瓶颈之一，直接影响能够处理的任务复杂度

2.2 大模型的局限性#

  1. 无法获取时效性的信息（训练数据截止日期之后的内容）
  2. 无法访问用户的私有数据（本地文件、个人数据库等）

2.3 解决方案#

2.3.1 RAG（检索增强生成）#
  • 全称：Retrieval-Augmented Generation
  • 工作原理：从外部知识库中检索相关信息，注入到上下文窗口中，供大模型参考使用
  • 适用场景：需要基于特定知识库回答问题的场景
2.3.2 函数调用（Function Calling）#
  • 工作原理：大模型根据用户需求，自主判断是否需要调用外部工具
  • 执行流程：
    1. 判断是否需要调用外部信息
    2. 选择合适的外部 API
    3. 生成符合 API 要求的参数格式
    4. 由外部环境执行 API 调用并返回结果
    5. 大模型根据返回结果生成最终回复
  • 说明：大模型不需要编写调用函数的代码，它的任务在于理解用户需求并进行逻辑推理，决定调用哪个工具函数

三、工具与生态#

3.1 Prompt 与提示词工程#

  • Prompt（提示词）：大模型接收的具体问题或指令
  • 主要分类：
    • User Prompt：用户输入的具体任务说明
    • System Prompt：后台配置的人设和做事规则
  • Prompt Engineering（提示词工程）：通过优化提示词来提高大模型输出质量的技术

3.2 Tool（工具）#

  • 定义：大模型用来感知和影响外部环境的函数
  • 作用：扩展大模型的能力边界，让模型能"动手"执行任务
  • 示例：搜索工具、计算器、文件操作工具、API 调用工具等

3.3 MCP（模型上下文协议）#

  • 全称：Model Context Protocol
  • 定义：统一的工具接入规范
  • 出现背景：各家大模型内置的 Function Calling 没有统一的标准，导致工具复用困难
  • 运行逻辑：
    1. MCP 服务端有规定好的工具列表
    2. MCP 客户端向 MCP 服务端请求工具（服务端返回工具列表）
    3. 大语言模型（MCP host）向 MCP 客户端申请调用（即初始化客户端）
    4. 会话建立
  • 简化流程：模型触发操作（host）→ 调用工具获取资源（客户端）→ 返回资源响应（服务端）→ 返回给模型（客户端）

四、高级架构#

4.1 Agent（智能体）#

  • 定义：能够自主规划、自主调用工具直至完成用户任务的系统
  • 核心能力：
    • 感知：理解用户意图和环境信息
    • 决策：制定任务执行计划
    • 反馈：与用户确认关键信息
    • 执行：调用工具完成具体操作
  • 示例（购物 Agent）：
    1. 感知：自主询问用户的购物意图（查询数据库、文件）
    2. 决策：自主根据用户购物喜好列出物品清单
    3. 反馈：和用户确认商品以及商品数量
    4. 执行：自主调用 API 到购物平台购买商品、操作本地文件、执行系统命令等

4.2 Agent Skill（智能体技能）#

  • 定义：封装了特定任务执行逻辑和相关工具调用规则的可复用能力模块
  • 组成：通常包含说明文档、工具选择策略和参数生成模板
  • 传统问题：如果 MCP 返回所有的工具列表给智能体，智能体需要询问大模型应该用哪一个工具，这会占用大量上下文窗口，浪费 Token
  • 解决方案：
    • 通过文件配置的形式为 Agent 赋予专业知识能力（元数据加载）
    • 让 Agent 知道哪个工具最适合当前任务，甚至如何组合使用多个工具
    • 按需加载：当需要使用某个技能时，Agent 才加载该技能的详细指令和相关工具信息，避免一次性加载所有内容

4.3 多 Agent 协作#

  • 适用场景：复杂任务处理，需要"专业的人做专业的事"
  • 实现方式：通过A 2 A (Agent-to-Agent) 通信协议实现 Agent 之间的信息交换和任务协调
  • A 2 A 协议：主要用于远程 Agent 之间的通信
  • 协调者角色：通常需要一个主 Agent 作为协调者，负责：
    • 任务分解
    • 资源分配
    • 数据交互
    • 状态同步
    • 结果汇总

五、核心概念关系总结#

概念核心作用关键影响
Token基础处理单位决定成本和长度限制
Context Window临时记忆容量影响任务复杂度
Prompt人机沟通桥梁决定输出质量
Tool能力扩展接口让模型能"动手"
MCP工具接入标准统一工具生态
Agent整体执行架构实现自主任务执行
Agent Skill能力高级封装提供可复用的能力模块
